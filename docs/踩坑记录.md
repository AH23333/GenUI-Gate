## PIT-001 Windows CRLF 会破坏跨平台哈希确定性

- **日期**：2026-11-03
- **现象**：`git add .gitignore` 时警告 `LF will be replaced by CRLF`。
- **根因**：Windows git 默认 `core.autocrlf` 行为，检出/暂存时改写换行符。
- **为什么对本项目是实质风险**：canonical JSON 与 fixture 的跨平台哈希一致性（v2 §15.1）要求同一内容在任何平台产生相同字节。若 fixture 被 CRLF 污染，Windows 与 Linux CI 对同一文件算出不同哈希，确定性测试会"莫名"变红。
- **修复**：`.gitattributes` 强制 `* text=auto eol=lf`（提交 dc1ee89），Windows 检出也保持 LF。
- **衍生要求**：fixture 生成代码中如遇换行符敏感内容，一律显式 `\n`，禁依赖平台默认。

## PIT-002 pnpm 全局 shim 与多版本 Node 并存

- **日期**：2026-11-03
- **现象**：`pnpm --version`（11.7.0）与 `npm --version`（11.7.0）输出相同；`Get-Command pnpm` 指向 `D:\NVM\nvm\v22.20.0\node_global\pnpm.ps1`，而当前 Node 是 v24。
- **根因**：pnpm 经 nvm 管理的旧版 Node 的全局目录安装；本机存在多套 Node。
- **影响**：pnpm 在当前 shell 可用（本次开发验证通过）；但换 shell/换 Node 版本后 pnpm 可能消失或行为变化。
- **规避**：交接时记录依赖 pnpm v11 + Node ≥ 20（交接文档 §3）；若 pnpm 失效，`npm i -g pnpm` 重装即可，仓库本身无影响。

## PIT-003 pnpm 11 拦截依赖构建脚本，且配置位置多次变迁

- **日期**：2026-11-03
- **现象**：`pnpm install` 报 `[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild@0.28.2`；随后 `pnpm exec`（tsc/vitest）因前置的 deps-status 检查重跑 install 失败而完全不可用。
- **根因**：pnpm 10+ 默认不执行依赖的 postinstall 脚本（供应链防护）。且配置位置变迁：`package.json#pnpm.onlyBuiltDependencies` 在 pnpm 11 已废弃（警告），新位置是 `pnpm-workspace.yaml` 的 `onlyBuiltDependencies`；但已缓存了"被忽略"状态的 `node_modules` 需要显式批准才能清除。
- **修复**：`pnpm approve-builds esbuild`（交互式批准，写回 `pnpm-workspace.yaml` 的 `allowBuilds`）；同时在 workspace yaml 保留 `onlyBuiltDependencies: [esbuild]`（pnpm 10/11 双兼容）。
- **衍生要求**：新依赖若带构建脚本，安装后留意 ignored-builds 警告；CI 用 `--frozen-lockfile` 时同样依赖 yaml 里的批准配置。

## PIT-004 aliased `typeof` 收窄在 `unknown` 上不可靠

- **日期**：2026-11-03
- **现象**：`const type = typeof x; if (type !== 'object') ...` 之后使用 `x`，TS 报 `{} | undefined` 不可赋给 `object`——aliased 条件收窄未生效。
- **根因**：TS 4.4+ 的 aliased condition 收窄对 `unknown` 起点类型的 `typeof` 别名支持不完整（尤其在解构绑定上）。
- **修复**：改用直接 `typeof x === 'object'` 判断（提交 5b90033 的 json.ts）。
- **衍生要求**：对 `unknown` 做类型分派时一律写直接 `typeof` 判断，不用别名；lint 无强制，靠 review。

## PIT-005 官方 A2UI 语料的 `version` 字段不可用于严格校验

- **日期**：2026-11-04
- **现象**：上游仓库的黄金语料中 version 值不一致：v0.9.1 的 contact_form JSONL 实际写 `"v0.9"`（非 `"0.9.1"`），而 v1.0 schema 将 version 定为 const `"1.0"`；且 v0.9.1 的消息命名（`server_to_client_*`）与 v1.0（`createSurface` 等）完全不同。
- **根因**：协议早期版本未约束 version 格式（v0.9.1 里是自由字符串），官方示例自身就没按后来的 const 约定写。
- **为什么重要**：若 adapter 或 audit 按 version 严格分派/校验，官方自家 fixtures 会被拒——对"官方 samples 能出报告"的 M0 出口是致命的。
- **修复**：adapter 只**记录** version 不校验；消息语义按字段名自适应识别，不依赖 version 分派（任务 0.7 的 parse.ts）。
- **衍生要求**：M1 若引入 schema 校验，version 校验必须是警告级（warning/requireApproval），不得 block；任何"按版本分派"的逻辑改为"按字段存在性探测"。

## PIT-006 Node 24 下 tsx 启动器的两连坑：旧 loader 钩子已死 + Windows `--import` 绝对路径按 URL 解析

- **日期**：2026-11-04
- **现象**：无构建步骤运行 TS CLI，`register('tsx/esm', url)` 在 Node 24 直接抛 `tsx must be loaded with --import instead of --loader`；改为 spawn `node --import <tsxEntry绝对路径>` 后 Windows 抛 `ERR_UNSUPPORTED_ESM_URL_SCHEME ... Received protocol 'd:'`。
- **根因**：① Node ≥20.6 弃用 `--loader` 钩子链，tsx 的旧 ESM 入口走的是 deprecated API，Node 24 已不可用；② `--import` 的值按模块说明符/URL 解析，Windows 绝对路径 `D:\...` 的盘符被当成 URL 协议。
- **修复**：bin shim 改为 spawn `node --import pathToFileURL(require.resolve('tsx')).href <entry>`（等价 tsx 官方用法 `node --import tsx`，但绝对 file:// URL 化以跨 cwd/跨平台，提交见任务 0.8）。
- **衍生要求**：任何 Node 模块定制一律用 `--import` / `module.register()` 新 API，不碰 `--loader` / `tsx/esm`；给 `--import`/`--loader` 传本地路径必须 `pathToFileURL()` 转换。

## PIT-007 高负载下 vitest 全量套件偶发超时 flake（spawn 集成测试）

- **日期**：2026-11-04
- **现象**：提交前门禁 `pnpm test` 偶发整体失败（exit 1），当次 Duration 22s（正常 ~6s，transform/collect 时间 2~3 倍膨胀）；立即复跑两次均 188/188 全绿。
- **根因**：机器高负载（多进程并行抢 CPU）时 vitest transform/collect 变慢，cli.test.ts 的 spawn 集成测试（真起子进程跑 CLI）叠加 30s testTimeout 兜底仍可能超时——既有 flake 模式的加重复发（0.8 时已把该文件 testTimeout 提到 30s）。
- **为什么重要**：提交门禁被 flake 卡住会造成"假红"；反之若用 `;` 串接命令还会造成"测试红了但提交已落"的纪律破坏（本次 0e0d637 即中招，docs-only 变更无实质影响，两次复跑全绿确认）。
- **修复/规避**：① 门禁命令必须条件串接（PowerShell 用 `if ($?)`，bash 用 `&&`），杜绝"红着也提交"；② 遇整体 Duration 异常膨胀的偶发失败，先复跑一次再排查，不急于改代码；③ CI 首跑后观察 ubuntu/windows 是否复现，若复现考虑给 spawn 类测试单独 `pool: 'forks'` 或提高并行隔离。
- **衍生要求**：本地"全绿"结论以复跑确认为准；失败日志必须保留失败用例名（本次输出被截断未留到用例名，属流程瑕疵，后补记录）。
