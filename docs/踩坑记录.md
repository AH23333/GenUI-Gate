## PIT-001 Windows CRLF 会破坏跨平台哈希确定性

- **日期**：2026-11-03
- **现象**：`git add .gitignore` 时警告 `LF will be replaced by CRLF`。
- **根因**：Windows git 默认 `core.autocrlf` 行为，检出/暂存时改写换行符。
- **为什么对本项目是实质风险**：canonical JSON 与 fixture 的跨平台哈希一致性（v2 §15.1）要求同一内容在任何平台产生相同字节。若 fixture 被 CRLF 污染，Windows 与 Linux CI 对同一文件算出不同哈希，确定性测试会"莫名"变红。
- **修复**：`.gitattributes` 强制 `* text=auto eol=lf`（提交 dc1ee89），Windows 检出也保持 LF。
- **衍生要求**：fixture 生成代码中如遇换行符敏感内容，一律显式 `\n`，禁依赖平台默认。

## PIT-002 pnpm 全局 shim 与多版本 Node 并存

- **日期**：2026-11-03
- **现象**：`pnpm --version`（11.7.0）与 `npm --version`（11.7.0）输出相同；`Get-Command pnpm` 指向 `D:\NVM\nvm\v22.20.0\node_global\pnpm.ps1`，而当前 Node 是 v24。
- **根因**：pnpm 经 nvm 管理的旧版 Node 的全局目录安装；本机存在多套 Node。
- **影响**：pnpm 在当前 shell 可用（本次开发验证通过）；但换 shell/换 Node 版本后 pnpm 可能消失或行为变化。
- **规避**：交接时记录依赖 pnpm v11 + Node ≥ 20（交接文档 §3）；若 pnpm 失效，`npm i -g pnpm` 重装即可，仓库本身无影响。

## PIT-003 pnpm 11 拦截依赖构建脚本，且配置位置多次变迁

- **日期**：2026-11-03
- **现象**：`pnpm install` 报 `[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild@0.28.2`；随后 `pnpm exec`（tsc/vitest）因前置的 deps-status 检查重跑 install 失败而完全不可用。
- **根因**：pnpm 10+ 默认不执行依赖的 postinstall 脚本（供应链防护）。且配置位置变迁：`package.json#pnpm.onlyBuiltDependencies` 在 pnpm 11 已废弃（警告），新位置是 `pnpm-workspace.yaml` 的 `onlyBuiltDependencies`；但已缓存了"被忽略"状态的 `node_modules` 需要显式批准才能清除。
- **修复**：`pnpm approve-builds esbuild`（交互式批准，写回 `pnpm-workspace.yaml` 的 `allowBuilds`）；同时在 workspace yaml 保留 `onlyBuiltDependencies: [esbuild]`（pnpm 10/11 双兼容）。
- **衍生要求**：新依赖若带构建脚本，安装后留意 ignored-builds 警告；CI 用 `--frozen-lockfile` 时同样依赖 yaml 里的批准配置。

## PIT-004 aliased `typeof` 收窄在 `unknown` 上不可靠

- **日期**：2026-11-03
- **现象**：`const type = typeof x; if (type !== 'object') ...` 之后使用 `x`，TS 报 `{} | undefined` 不可赋给 `object`——aliased 条件收窄未生效。
- **根因**：TS 4.4+ 的 aliased condition 收窄对 `unknown` 起点类型的 `typeof` 别名支持不完整（尤其在解构绑定上）。
- **修复**：改用直接 `typeof x === 'object'` 判断（提交 5b90033 的 json.ts）。
- **衍生要求**：对 `unknown` 做类型分派时一律写直接 `typeof` 判断，不用别名；lint 无强制，靠 review。

## PIT-005 官方 A2UI 语料的 `version` 字段不可用于严格校验

- **日期**：2026-11-04
- **现象**：上游仓库的黄金语料中 version 值不一致：v0.9.1 的 contact_form JSONL 实际写 `"v0.9"`（非 `"0.9.1"`），而 v1.0 schema 将 version 定为 const `"1.0"`；且 v0.9.1 的消息命名（`server_to_client_*`）与 v1.0（`createSurface` 等）完全不同。
- **根因**：协议早期版本未约束 version 格式（v0.9.1 里是自由字符串），官方示例自身就没按后来的 const 约定写。
- **为什么重要**：若 adapter 或 audit 按 version 严格分派/校验，官方自家 fixtures 会被拒——对"官方 samples 能出报告"的 M0 出口是致命的。
- **修复**：adapter 只**记录** version 不校验；消息语义按字段名自适应识别，不依赖 version 分派（任务 0.7 的 parse.ts）。
- **衍生要求**：M1 若引入 schema 校验，version 校验必须是警告级（warning/requireApproval），不得 block；任何"按版本分派"的逻辑改为"按字段存在性探测"。

## PIT-006 Node 24 下 tsx 启动器的两连坑：旧 loader 钩子已死 + Windows `--import` 绝对路径按 URL 解析

- **日期**：2026-11-04
- **现象**：无构建步骤运行 TS CLI，`register('tsx/esm', url)` 在 Node 24 直接抛 `tsx must be loaded with --import instead of --loader`；改为 spawn `node --import <tsxEntry绝对路径>` 后 Windows 抛 `ERR_UNSUPPORTED_ESM_URL_SCHEME ... Received protocol 'd:'`。
- **根因**：① Node ≥20.6 弃用 `--loader` 钩子链，tsx 的旧 ESM 入口走的是 deprecated API，Node 24 已不可用；② `--import` 的值按模块说明符/URL 解析，Windows 绝对路径 `D:\...` 的盘符被当成 URL 协议。
- **修复**：bin shim 改为 spawn `node --import pathToFileURL(require.resolve('tsx')).href <entry>`（等价 tsx 官方用法 `node --import tsx`，但绝对 file:// URL 化以跨 cwd/跨平台，提交见任务 0.8）。
- **衍生要求**：任何 Node 模块定制一律用 `--import` / `module.register()` 新 API，不碰 `--loader` / `tsx/esm`；给 `--import`/`--loader` 传本地路径必须 `pathToFileURL()` 转换。

## PIT-007 高负载下 vitest 全量套件偶发超时 flake（spawn 集成测试）

- **日期**：2026-11-04
- **现象**：提交前门禁 `pnpm test` 偶发整体失败（exit 1），当次 Duration 22s（正常 ~6s，transform/collect 时间 2~3 倍膨胀）；立即复跑两次均 188/188 全绿。
- **根因**：机器高负载（多进程并行抢 CPU）时 vitest transform/collect 变慢，cli.test.ts 的 spawn 集成测试（真起子进程跑 CLI）叠加 30s testTimeout 兜底仍可能超时——既有 flake 模式的加重复发（0.8 时已把该文件 testTimeout 提到 30s）。
- **为什么重要**：提交门禁被 flake 卡住会造成"假红"；反之若用 `;` 串接命令还会造成"测试红了但提交已落"的纪律破坏（本次 0e0d637 即中招，docs-only 变更无实质影响，两次复跑全绿确认）。
- **修复/规避**：① 门禁命令必须条件串接（PowerShell 用 `if ($?)`，bash 用 `&&`），杜绝"红着也提交"；② 遇整体 Duration 异常膨胀的偶发失败，先复跑一次再排查，不急于改代码；③ CI 首跑后观察 ubuntu/windows 是否复现，若复现考虑给 spawn 类测试单独 `pool: 'forks'` 或提高并行隔离。
- **衍生要求**：本地"全绿"结论以复跑确认为准；失败日志必须保留失败用例名（本次输出被截断未留到用例名，属流程瑕疵，后补记录）。

## PIT-008 renderText 终端转义注入：输入派生字符串裸拼进报告

- **日期**：2026-11-04
- **现象**：探针实测 `surfaceId` 含 `\x1b]0;pwned\x07` 时 `renderText` 输出原样带出 ESC 序列——可改终端标题、清屏；含 `\r`/`\n` 的 id 可伪造报告行（如插入假的 `Overall: PASS`）。`--json` 路径免疫（`JSON.stringify` 转义控制字符）。
- **根因**：文本渲染层未区分内部字符串与输入派生字符串；surfaceId/catalogId/issue 消息（含组件 id 插值）直接进 `lines.push` 模板。
- **修复**：`report.ts` 新增 `safeText()`，一切输入派生字符串插值前剥离全部 C0 + DEL（`\x00-\x1F\x7F`，含 `\n`——防伪造行）；`lines.join('\n')` 的行分隔符不受影响。回归锁 = audit 属性测试 "renders hostile ids without leaking any control character"（EVIL 集：`\x1b`、`\x1b[2J`、OSC 标题序列、`\r`、`\n`、`\x00`、`\x07`、`\x7f`）。
- **发现途径**：深测前置探针（先怀疑 → 一次 `npx tsx --eval` 实测确认 → 再写性质测试与修复），比"先写测试看红"更快定位。
- **衍生要求**：一切人类可读渲染（M1 session 预览、M2 公开报告）沿用"输入派生字符串先消毒"；审计层两条输出路径（text/JSON）安全性质分别显式测试，不假设其一覆盖另一。

## PIT-009 pointer 层原型链污染：`__proto__` 写入 `Object.prototype` + 继承属性混淆

- **日期**：2026-11-04
- **现象**：深测属性测试（fast-check）反例 `tokens=["toString",""]` 使 `pointerSet('/toString/', 0)` 抛 `PointerError`——`container[token] !== undefined` 走了原型链读到继承的 `toString` 函数。更严重：`pointerSet(doc, '/__proto__/polluted', 'x')` 经 `resolve` 把 `doc['__proto__']`（继承的 `Object.prototype`）当中间容器，**直接污染全局原型**；而 `updateDataModel.path` 是 agent 输入，构成真实攻击面（恶意 spec 可污染宿主进程所有对象）。
- **根因**：① 对象读写用 bracket 访问走原型链，但 JSON 文档语义下对象没有原型（RFC 6901 求值不应看见 `toString`/`constructor`）；② `obj['__proto__'] = v` 触发原型 setter 而非创建 own 键。
- **修复**：`pointer.ts` 全面 own-property 语义——读用 `Object.hasOwn` 判定（继承属性视为不存在）、中间容器与最终赋值一律 `Object.defineProperty`（绕开 `__proto__` setter，`__proto__` 令牌成为 own JSON 键而非原型交换）、null 删除前先 `hasOwn` 判定。确定性回归测试 ×2（污染路径 + 继承混淆）+ 属性往返覆盖（`pointerSet`→`pointerGet` 任意路径）。
- **发现途径**：属性测试随机种子命中（连续两轮绿、第三轮抓到），说明**纯靠确定性用例测不出这类分支**；深测属性 ≥100 runs 是必要层。
- **衍生要求**：任何以输入派生字符串为键的对象读写一律 `hasOwn`/`defineProperty`，禁裸 bracket 写；adapter 的组件/surface 索引用 `Map` 本就免疫（本次一并核查确认）；M1 policy 若读 props 对象，沿own-property 语义。

## PIT-010 CI 首跑揭出测试 helper 的 own-property 丢失：`reverseKeys` 丢 own `__proto__` 键 + node 20/pnpm 11 不兼容

- **日期**：2026-11-04
- **现象**：公开仓库 CI 首跑 CI #1（commit 2ea065b）4 job 全挂：① node 20 ×2 在 pnpm/setup 阶段即挂——`pnpm@11.7.0` 要求 Node ≥22.13（`node:sqlite` builtin 缺失）；② node 22 ×2（ubuntu 挂 Coverage 步、windows 挂 Test 步，同一根因）在 ir `hash.test.ts` 键序不变性属性失败，fast-check 反例 `{["__proto__"]: false}`，收到的哈希是 sha256(`"{}"`)——copy 侧键整个丢了。
- **根因**：测试 helper `reverseKeys`（ir/test/helpers.ts）/`reverseNodeKeys`（ir/test/hash.test.ts）重建对象用普通赋值 `out[key] = ...`——当生成的 JSON 含 own `__proto__` 键（fast-check `fc.jsonValue()` 抽中率实测 ~4/50000 ≈ 1/12500）时，赋值触发 `Object.prototype.__proto__` setter（非对象值被忽略），键静默丢失。库本身安全（`canonicalize` 用 `Object.keys` 枚举 + bracket 读 own 键，无重建写路径）。与 KAN-016/PIT-009 同一语义类：**凡"以动态键重建对象"的代码，普通赋值都会丢 own `__proto__` 键**。
- **为什么本地没拦住**：键生成概率 ~1/12500/次，属性 200 runs/轮的命中期望 <2%，本地多轮全绿属正常抽样；CI 两 node 22 job 同轮命中是低概率坏运气但**性质上必然复现**——这正是性质测试的价值，也是"属性发现必须配确定性回归"的原因。
- **修复**：helper 重建改 `Object.defineProperty`（enumerable/writable/configurable 显式）；确定性回归 ×2（canonicalize 保留 own `__proto__` 键输出 `{"__proto__":false}`；canonicalHash 键序不变含 `__proto__`，断言 `Object.keys(copy)` 键存活）；CI 矩阵 node 20 → 22、根 engines `>=20` → `>=22.13`（KAN-017）。
- **发现途径**：CI 首跑（TD-002 验证本身）。本地复现探针（Node 24）：`JSON.parse`/`JSON.stringify`/`structuredClone`/`Object.fromEntries` 均保留 own `__proto__` 键，唯普通赋值丢失——排除 clone 环节嫌疑。
- **衍生要求**：① 测试 helper 重建动态键对象一律 `defineProperty`/`fromEntries`，禁普通赋值（与 KAN-016 纪律合并执行）；② `engines`/`packageManager`/CI 矩阵三者的 Node 版本约束必须联动检查（pnpm major 升级时先查其 Node 下限）；③ 新增随机性质测试跑绿后，可在 CI 或本地加大 numRuns 抽查一次再提交。

## PIT-011 本机 git 凭据被外部工具后台轮换：lingxi credential store 覆盖用户 PAT + PowerShell 空参丢失

- **日期**：2026-11-04
- **现象**：向 GitHub push 连续两次 403（`Permission to AH23333/GenUI-Gate.git denied to AH23333.`）：第一次是把用户 PAT 写进 lingxi 的凭据文件 `C:/Users/34697/.config/lingxi/git-credentials` 后 push 成功，但下一次 push（fec77ac）又被拒——文件字节数不变（121 B），内容里的 token 却已被换回 lingxi 自己的（同 `github_pat_11BJ` 前缀，无本仓库写权限）。同时 `cmdkey /list` 里的 `git:https://github.com` 条目反复出现。
- **根因**：① 本机 `C:/Users/34697/.gitconfig` 存在 per-URL 凭据配置（`credential.https://github.com/.helper` = 空值重置 + `store --file=<lingxi 凭据文件>`），对 github.com 的凭据查询绕开 Git Credential Manager、只走 lingxi 文件；② lingxi 工具在后台周期性轮换自己凭据文件里的 token——**和它抢写同一文件必输**；③ 排查工具本身有坑：PowerShell 5.1 管道给 `git credential fill` 喂 stdin 会因编码/换行差异解析失败（须写临时文件经 `cmd /c "git credential fill < file"` 重定向），且 PowerShell 向原生命令传空字符串参数会被静默丢弃（`git config key ""` 报 `wrong number of arguments`）。
- **修复（PIT-011 落地架构）**：不碰 lingxi 的文件与其全局配置——① 建本项目专属凭据文件 `C:/Users/34697/.config/genui-gate/git-credentials`（用户 PAT，LF + 尾换行）；② 本仓库 `.git/config` 追加同名 per-URL 配置：空值 `helper`（重置，清掉 global 累积的 lingxi store）+ `helper = store --file=<专属文件>`——多值配置按 system→global→local 顺序累积，local 的空值重置使其后的 local store 成为 github.com 的唯一生效链；lingxi 的全局配置与其他仓库不受影响。生效链用 `git config --show-origin --get-all credential.https://github.com/.helper` 验证（4 行：2 global + 2 local，空值在 local store 之前）。
- **为什么重要**：凭据竞争是环境级问题，不解决则每次 push 都可能随机 403，且极易误诊为"PAT 失效/权限配错"反复换 token。判断 PAT 本身是否有效的最短路径是直接 `curl -H "Authorization: Bearer <token>"` 打 API 看 HTTP 码，不经过 git 凭据链。
- **衍生要求**：① 本项目凭据一律走专属文件 + repo-local 覆盖，不再写任何外部工具管理的凭据存储；② 给 git 命令传空字符串参数时改用直接编辑 `.git/config`（PowerShell 5.1 丢空参）；③ `git credential fill` 的 stdin 必须文件重定向（经 `cmd /c`），不用 PowerShell 管道；④ CI 状态查询优先 badge SVG（`actions/workflows/ci.yml/badge.svg`，免认证、不限流），详细数据用 PAT 认证打 Actions API（未认证 60 req/h 限流，403 时别误判为权限问题）。
