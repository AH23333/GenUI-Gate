# "Agent 编排 UI"构想 v1：协议无关的 GenUI 治理层

> 版本：v1（2026-11）｜ 前版：`构想v0.md`｜ 依据：`竞品调研-2026-11.md`｜ 工程设计：`产品设计v1.md`
>
> **v0 → v1 变更摘要**：
> 1. 核心叙事从"个性化布局"改为"**个性化信息编排**"（布局由模板保证，Agent 只选模板、填槽位）；
> 2. 定位从"A2UI 之上的治理运行时"改为"**协议无关的 GenUI 治理层**"（A2UI / MCP Apps / ChatKit 三极中立）；
> 3. 首个产品切口从通用治理改为"**可访问性硬 gate**"（法规驱动、无人竞争）；
> 4. 明确**双层用户模型**（开发者要 DX，企业要合规）与护城河重排（校验=获客，偏好数据/审计链/基准=护城河）；
> 5. 补齐四项技术决策：治理执行三阶段、协议防腐层、冲突仲裁模型、含组件状态的快照回滚；
> 6. MVP 范围收紧（2 组件 / 1 布局 / 1 场景 / 4 治理项 / 3 指标），评估指标拆为两代以解开冷启动死结；
> 7. 竞品参照系修正：移除无法验证的 Apex/begeniux，新增 ChatKit、AGenUI Studio、Thesys 转型。

---

## 一、想法本质

原始构想：做一个面向前端的框架，让 Agent 根据用户需求实时修改页面排版、元素和信息展示方式，不追求统一定式。

v1 定义：

> **一套协议无关的生成式 UI 治理层：不管 UI 声明来自 A2UI、MCP Apps 还是 ChatKit，都在渲染前经过同一道治理闸门——策略即代码、可访问性硬 gate、布局质量评估、快照回滚；并在渲染后形成用户偏好学习闭环。Agent 决定"展示什么、什么顺序、什么粒度"，布局质量由人工模板保证。**

设计原则：

1. Agent 不写 DOM/代码，只输出 UI 声明（spec）；治理层与协议解耦，协议可替换。
2. **个性化信息编排，而非个性化空间布局**：v0 自己引用的证据（Apple CHI 2026："布局和层级，而非语法，是 LLM 的主导性弱点"）否定了让 Agent 直接排版。因此布局一律来自人工设计的模板库，Agent 只做**模板选择 + 槽位填充 + 数据映射**。Agent 的职责范围与其能力边界对齐：布局质量由人保证，编排价值由 Agent 提供。
3. 治理三阶段：**编译期**（组件目录预审计）→ **渲染期**（schema + a11y gate，客户端执行，保延迟与信任）→ **渲染后**（质量指标异步采集）。治理不进入服务端串行链路。
4. 每次变更有快照、可解释、可回滚、可锁定、可灰度；快照必须包含组件状态（输入值、滚动位置、进行中请求），否则回滚机制形同虚设。
5. 稳定骨架 + 受约束可变区域；冲突仲裁有显式优先级（见五-3）。

## 二、市场结论摘要（详见竞品调研-2026-11.md）

1. **协议层三极分化**：A2UI（开放，v0.9.1 现行 / v1.0 候选，Google Opal/Gemini Enterprise/Flutter GenUI/ADK 生产部署）、MCP Apps（SEP-1865 已 Final，iframe 模型）、ChatKit（OpenAI 新入场）。协议越多，中立治理层价值越大。
2. **基础治理正被各层免费内建**：A2UI 协议自带校验；AG2 A2UIAgent 内置 schema 校验 + 重试；Thesys OpenUI Cloud 打包 validation/fallback/observability/合规认证。**"校验 + 白名单"没有独立产品机会，窗口 6-12 个月内关闭。**
3. **真正没人做的**：可访问性硬 gate、策略即代码、含组件状态的快照回滚、布局质量评估基准、跨协议中立治理、偏好学习闭环。
4. **v0 竞品论据修正**：Apex（Trust Runtime）与 begeniux 经多渠道检索无法验证，从竞品列表移除；json-render 被 Vercel 收编、Thesys 转型全栈平台、AGenUI 占据三端原生渲染——独立渲染/中间层玩家均在向平台靠拢，进一步印证"不做渲染、只做治理"的选择。
5. **合规被验证为付费点**：Thesys 挂 GDPR/SOC 2/ISO 27001 卖企业版，但**无人做 a11y 合规**——而 GenUI 的 WCAG 合规率仅约 29%，欧盟 EAA 已生效。这是有付费方、有法规 Deadline、无竞争者的切口。

## 三、定位

**一句话定位：**

> 面向前端开发者的协议无关 GenUI 治理层：任何协议的 UI 声明，渲染前过治理闸门（策略即代码、a11y 硬 gate、质量评估），渲染后进偏好闭环；为前端提供 5 分钟接入的 DX，为企业提供合规与审计。

**不做：**
- 不做新前端框架、不做新 UI 协议、不做渲染器（渲染层已被 A2UI 生态、AGenUI、各框架占据）；
- 不做"Agent 任意改 DOM/样式"的自由生成；
- 不做单纯的 schema 校验器（正在被协议/框架免费内建，无独立机会）；
- 不追求全站实时编排。

**要做（按优先级）：**
1. 可访问性硬 gate（首切口，法规驱动）；
2. 策略即代码（policy-as-code）的渲染期闸门；
3. 含组件状态的快照与回滚；
4. 布局/质量评估基准（"GenUI 界的 Lighthouse"，标准卡位）；
5. 用户锁定、偏好学习闭环（数据资产）；
6. 协议 adapter：A2UI → MCP Apps → ChatKit 渐进覆盖。

**双层用户模型（解决"谁采用、谁付费"）：**

| 受众 | 卖点 | 形态 |
|---|---|---|
| 前端开发者 | 5 分钟接入、组件目录工具链、预览调试、治理是免费副产品 | 开源核心（Apache 2.0） |
| 平台/企业架构师 | 策略即代码、审计证据链、a11y/合规报告 | 商业版（策略管理 + 审计 + 合规报表） |

## 四、护城河与商业化

明确区分**获客手段**与**护城河**，两者不可混淆：

| 能力 | 性质 | 说明 |
|---|---|---|
| 校验、白名单、fallback | 获客手段 | 会被协议层免费内建，做成开源核心的"入口功能" |
| 偏好学习数据（锁定/调整/回滚行为流） | **护城河** | 随使用积累的个性化数据壁垒，协议层永远不会做 |
| 审计证据链 | **护城河** | 合规场景的不可抵赖记录；Thesys 做平台内合规，无人做可嵌入的独立审计层 |
| 质量评估基准 | **护城河** | 若成为"GenUI 质量评测"事实标准（对标 Lighthouse），则标准即卡位 |
| 跨协议中立 | **护城河** | 单协议治理会被协议内建能力吞掉；三极分化使中立层无法被任何一家吸收 |

商业化路径：开源核心（gate + 目录工具 + React/Vue adapter）→ 企业版（策略管理、审计、合规报表）→ 基准/认证（质量标签、a11y 合规认证）。

## 五、技术决策（v0 未定，v1 必须先定）

### 1. 治理执行位置：三阶段，客户端为准
- **编译期**：组件目录预审计（a11y、性能预算、设计令牌合规在组件入库时一次性完成——"让安全的路成为唯一的路"）；
- **渲染期**：schema + 组合级 a11y 检查（标题层级、landmark 结构、焦点顺序）+ 策略闸门，全部在客户端执行，保证延迟与信任，不依赖服务端可用性；
- **渲染后**：质量指标（回滚率、锁定率等）异步采集，不阻塞渲染。

### 2. 协议防腐层
A2UI 仍处于 pre-1.0 快速演进期（v0.9 → v0.9.1 → v1.0 候选仅数月）。内部使用独立的 spec 模型，A2UI/MCP Apps/ChatKit 类型一律经 adapter 转入，**协议类型不得泄漏到核心代码库**，保证协议可替换。

### 3. 冲突仲裁模型（显式一等概念）
用户手动定制、Agent 提议、平台 A/B 实验、多 Agent 输出竞争同一区域时，按固定优先级仲裁：

> **用户锁定 > 用户偏好 > 平台策略 > Agent 提议**

仲裁结果可解释（"为什么这样展示"由 diff 与规则推导，不用 LLM 自由发挥生成解释）。

### 4. 快照与回滚：包含组件状态
回滚不仅是 spec 回滚。快照对象 = UI spec + 组件实例状态（表单输入、滚动位置、焦点）+ 进行中请求的取消/恢复策略。这是快照机制真正的技术难点，需在 MVP 中验证而非留待后期。

### 5. 可访问性：架构化，不是事后检查
依据 2026 年研究（显式要求 a11y 反而降低合规率），a11y 不进入 prompt、不依赖 LLM 自觉，而是：
- catalog 级：组件入库前预审计（对比度、语义标签，组件级问题组织级传播，入库拦截）；
- 组合级：渲染期检查标题层级、landmark、焦点顺序；
- 报告级：输出 WCAG/EAA 合规证据，对接企业版审计。

## 六、MVP 路线（收紧版）

v0 的 MVP（8 组件 × 3 布局 × 全套治理 × 全套指标）对 3-6 个月过大。收紧为：

| 维度 | v0 方案 | v1 收紧方案 |
|---|---|---|
| 场景 | 多选垂直场景 | **只选运维/数据看板**（结构化程度最高，LLM 出错空间最小） |
| 组件 | 5-8 个 | **2 个**（表格 + 卡片列表） |
| 布局原语 | 2-3 种 | **1 种**（单列主从） |
| 治理 | 全套 | **4 项**：schema 校验、白名单、a11y gate、快照回滚 |
| 指标 | 全套 | **3 项**：回滚率、锁定率、gate 通过率 |
| 协议 | A2UI 优先 | A2UI adapter + 防腐层（内部 spec 模型） |
| 前端 | React adapter | React adapter（一个） |

执行顺序：
1. 组件目录 + 预审计工具链（2 组件）；
2. 渲染期 gate（schema + a11y 组合检查）+ 快照回滚（含组件状态）；
3. Agent 链路："建议编排 → 校验 → 用户确认 → 应用"，模板选择 + 槽位填充；
4. 第一代指标埋点与看板；
5. （验证通过后）扩展策略即代码、更多协议 adapter。

**MVP 要验证的唯一核心命题**：
> "Agent 建议 → 校验 → 确认 → 可回滚"闭环跑通后，**回滚率与锁定率是否随时间下降**（即编排质量是否在学习中上升），且 a11y gate 拦截率是否收敛（即 Agent 是否学会绕开违规模式）。

这条命题成立，其余能力渐进叠加；不成立，方向即否。

## 七、评估指标：两代体系（解冷启动死结）

v0 的 Go/No-Go 依赖任务完成率、信息查找时间等需用户规模才能测的指标，存在"没用户→没指标→无法证明价值→没用户"死结。拆为两代：

**第一代（无用户即可算，运行时日志直接产出，上线第一天可测）：**
- schema 校验通过率、a11y gate 通过率与拦截率；
- 首次有效 spec 生成耗时、Agent 重试次数；
- 回滚率、锁定率、"恢复默认"点击率。

**第二代（第一代证明生成质量稳定后投入）：**
- 任务完成率、信息查找时间、错误率；
- 用户满意度、WCAG 合规率（人工审计抽样）。

## 八、风险与对冲

| 风险 | 概率 | 对冲 |
|---|---|---|
| 协议层把 a11y gate 内建（A2UI 1.x 或 ChatKit 内置） | 中 | 中立层定位本身就是对冲：单协议内建反而放大跨协议中立价值；同时用质量基准和偏好数据建立非协议依赖的资产 |
| a11y gate 误拦率高，开发者弃用 | 中 | gate 分级（error/warn）+ 可解释报告 + catalog 预审计降低组合检查负担；以"拦截可解释、误拦可申诉"为设计底线 |
| 治理层被视作摩擦，前端开发者不采用 | 高 | 双层模型：开发者侧治理为静默默认（预审计在入库时完成，渲染期无感），摩擦只对策略管理者可见 |
| A2UI v1.0 breaking change | 高 | 防腐层已列为一等架构决策 |
| 含状态快照的技术复杂度超预期 | 中 | 列为 MVP 显式验证项（六-4），失败则降级为"spec 快照 + 状态丢弃提示"，不隐瞒 |
| 三极格局进一步收敛（某家通吃） | 低 | 若发生，中立层价值短期受损，但审计/合规/偏好资产仍然协议无关 |

## 九、Go/No-Go 判断标准（更新）

在 **3-6 个月内**，于一个垂直场景（运维/数据看板）完成 MVP，并满足：

1. **闭环成立**："Agent 建议编排 → 校验 → 确认 → 可回滚"全链路跑通，无人工兜底；
2. **第一代指标**：回滚率、锁定率随使用周数呈下降趋势；a11y gate 拦截率收敛；首次有效 spec 生成 < 5 秒（模板路径，非自由生成）；
3. **开发者验证**：≥ 5 个外部开发者认为"没有这层不敢上生产"（治理层必要性成立），且接入耗时 < 30 分钟（DX 成立）；
4. **合规付费信号**：≥ 2 家企业愿为 a11y/审计报告进入付费沟通（商业模型成立）。

**四条全满足 → Go**：扩展协议 adapter、策略即代码、质量基准，向"GenUI 界的 Lighthouse + 审计层"演进。
**任一不满足 → No-Go 或 Pivot**：若 2 失败，说明 Agent 编排质量不可学习，方向否；若 4 失败，pivot 为纯开源治理工具（基准 + gate），放弃独立商业化。

## 十、结论

- 方向已被双重验证：协议生态爆发（A2UI 全线落地、中国三端开源）证明"Agent 声明 UI"是真实趋势；Thesys 合规认证收入证明企业为治理付费。
- 但**基础校验的独立产品窗口正在关闭**（6-12 个月），必须直接切入无人区：a11y 硬 gate、策略即代码、质量基准、偏好闭环。
- 差异化不在"更自由的生成"（撞 LLM 布局弱区），而在"**协议无关的治理与信任**"——三极分化（A2UI/MCP Apps/ChatKit）是这个定位成立的结构性前提，且该前提在 2026 年下半年刚刚形成。
- 最务实的形态：**开源 gate + 目录工具链获客，a11y/审计/策略企业版收费，质量基准卡位行业标准**；先在运维/数据看板单场景验证"回滚率下降"这一条命题，再横向扩展。
