# “Agent 实时编排 Web UI”构想整理

## 一、想法本质

原始构想：做一个面向前端的框架，让 Agent 根据不同用户需求，实时修改页面排版、元素和信息展示方式，打破固定页面和对话框形态，不追求统一定式。

更准确的重新定义：

> **不是“让 Agent 随便改页面”，而是做一套“受约束、可验证、可回滚的自适应 UI 运行时”。Agent 输出 UI 意图，框架负责安全渲染和治理。**

核心设计原则：

1. Agent 不直接写 DOM/代码，只输出 UI Spec/DSL。
2. 组件白名单 + 布局约束 + 设计令牌 + 性能预算 + 可访问性规则。
3. 稳定骨架 + 可变区域，避免用户每次进入都像换了一个产品。
4. 意图、规划、校验、渲染、反馈分层。
5. 每次布局变更有快照、可解释、可回滚、可锁定、可灰度。

## 二、市场现状：方向已被验证，但生态位尚未被完整占据

### 1. 协议/标准层：A2UI 是核心变量

Google A2UI 把界面描述为数据而非可执行代码，客户端用已有组件目录渲染。它支持 fixed-schema / dynamic-schema，框架无关，可流式增量渲染，已发布 v0.9。高德与阿里千问团队还基于 A2UI 开源了 AGenUI，覆盖 iOS、Android、HarmonyOS 原生渲染。

**意义**：你设想的“Agent 输出 UI Spec、框架安全渲染”已经有标准化基础。

### 2. 框架/SDK 层：CopilotKit、Tambo、Freesail、json-render、OpenUI

- **CopilotKit**：A2UI 主要集成方，提供 Agent 集成栈和 React/Angular renderer，并把 Generative UI 描述为从“完全作者控制”到“Agent invented”的光谱。
- **Tambo**：开源全栈 Generative UI 工具包，专注 React，组件注册后由模型动态渲染。
- **Freesail**：Agent-driven UI SDK，提供 React 和 Lit/Web Components 绑定。
- **json-render**：声明式 Generative UI 中间层，定义组件目录，Agent 生成 JSON spec，支持 React、Vue、Svelte、Angular。
- **OpenUI**：Agent 返回声明式语言写组件树，适合数据密集报告和仪表盘。

**意义**：框架层已有多个玩家，但分散，且多数偏 React 或单点能力。

### 3. 垂直产品/API：Thesys C1、begeniux、Apex

- **Thesys C1**：Generative UI API，让 LLM 返回交互式 UI 而非纯文本。
- **begeniux**：根据点击、滚动、悬停、停留时长等行为轨迹实时重渲染 UI，而不是只响应提示词。
- **Apex**：定位 Generative UI Trust Runtime，做声明式策略校验、安全组件词汇、禁止模型写原始 HTML/JS、防篡改审计链、持久化 human-in-the-loop。

**意义**：行为驱动和信任治理都已有产品验证，但 Apex 偏企业后端和 Rust 技术栈，给前端友好产品留了空间。

### 4. MCP 路径：MCP Apps 已存在，但治理层仍空白

MCP Apps 是 MCP 首个官方扩展，已 Final，工具通过 `_meta.ui.resourceUri` 声明 UI 资源，宿主在沙箱 iframe 中渲染，通过 postMessage 上的 JSON-RPC 通信。生态里还有 `mcp-gen-ui`、`bachstudio-gen-ui-mcp`、WebMCP Instrumentor 等形态。

但 MCP Apps 的 iframe 模型把 UI 控制权交给服务器，导致设计系统冲突、体验碎片化、安全边界模糊，宿主层面很难做统一治理。Google 正在考虑 “A2UI over MCP”：MCP 管工具和数据，A2UI 管 UI 声明和渲染。

**关键结论**：MCP 解决“UI 怎么从服务器到达客户端”的管道问题，不解决“UI 该长什么样、该不该被允许、改坏了怎么办”的治理问题。

## 三、真正的差距在哪里

| 你的设想要素 | 现有最接近产品 | 状态 |
|---|---|---|
| Agent 输出 UI Spec，不写 DOM/代码 | A2UI、json-render | 已有标准 |
| 组件白名单 + 约束空间 | A2UI catalog、CopilotKit | 已成熟 |
| 稳定骨架 + 可变区域 | A2UI fixed/dynamic schema | 已产品化 |
| 行为/角色驱动实时调整 | begeniux、CopilotKit | 已有实现 |
| 回滚、审计、human-in-the-loop | Apex Trust Runtime | 已有，偏企业后端 |
| 面向前端的完整框架/生态 | json-render、Tambo、Freesail | 有，但分散 |
| “不追求统一定式”的设计哲学产品化 | CopilotKit 光谱叙事最接近 | 部分覆盖 |
| **完整治理运行时：校验、回滚、可访问性 gate、布局质量评估、个性化评估** | **无完整产品** | **相对空白** |

**没有被充分占据的位置**：把协议、集成栈、信任运行时组合成面向前端开发者的开箱即用“自适应 UI 治理运行时”，并以“个性化布局”为核心叙事，而不是 Generative UI 的附带能力。

## 四、生态适配与实现难度：不能单纯乐观

### 1. A2UI 生态成熟度被高估

A2UI 与 REST、SSE、WebSockets 等常见传输方式“可行但尚未可用”，目前主要依赖 AG UI 通路。脱离 A2A 单独使用时，在连接握手与能力协商、多 surface 会话分组、非对称流配对、客户端-代理信任验证四个基础层面存在协议缺口。

### 2. CopilotKit 偏 React

AG UI 框架无关，但 CopilotKit 是 React-specific，json-render 在 CopilotKit 中的集成也仅支持 React 作为 BYOC。覆盖 Vue、Svelte、原生 Web Components 需要自建渲染层和开发者体验。

### 3. LLM 生成结构化 UI 慢且易错

Google 承认让 LLM 生成受复杂 JSON schema 约束的 JSON 树“慢且容易出错”。A2UI Express 声称延迟最多降低 3 倍，决策模型做布局决策可达 80 倍，Express token 少最多 3 倍——这些优化本身说明默认路径不达标。Flutter 团队采用异步预生成 + 缓存，启动时绕过 LLM，说明“真正实时”被压缩到数据变化触发的预计算。

### 4. 可靠性无法归零

OpenUI 团队基准测试覆盖 A2UI、json-render、OpenUI 自身，结论是每个被测格式都产生过不完整生成。OpenUI 在 1,104 次运行中完成 92.9% 任务，产生 2 个空白屏幕，最强模型配对达 99.5%，但不是 100%。框架必须内置运行时校验、自动修正和监控。

### 5. 可访问性是架构级冲突

2026 年两项独立研究：AI 生成 UI 组件存在缺失标签、不当 ARIA、焦点和键盘导航失败，缺陷进入共享设计系统会组织级传播；21,880 次评估中 AI 生成界面仅达 29.0% WCAG 合规率，色彩对比 26.8%、颜色使用 19.2% 最差；更反直觉的是，prompt 中显式要求可访问性反而降低合规率。可访问性必须编码进组件目录、渲染器和校验层，作为硬 gate。

### 6. 布局和层级是 LLM 最系统性弱点

Apple CHI 2026 基于 1,500 条设计师标注的研究结论：LLM “无法可靠地生成设计良好的 UI”，问题集中在字段错位、文本重叠、信息层级混乱，而不是语法错误。“布局和层级，而非语法，是主导性弱点。” 这恰好击中“Agent 直接修改页面排版”的核心诉求。

### 7. 学术研究已将其结构化为隐性技术债

CHI 2026 workshop 论文归纳 GenUI 生产化障碍为：数据共享复杂性、非自适应安全协议、用户技能差距与认知过载，导致 malleable interfaces 未被广泛采用，仍主要停留在研究原型。arXiv 论文点出缺乏可适配数据格式、“旧”安全协议不匹配、用户认知和创造技能缺口。W3C 中国 2026 年 1 月 GenUI 研讨会列出性能效率、安全风险、可扩展性、互操作性挑战。

## 五、“Web UI 的 MCP”这个类比需要修正

| 层面 | 类比是否成立 | 现实对应 |
|---|---|---|
| 传输/工具协议层 | 成立 | MCP 已承担 Agent 发现和调用“UI 能力”的通道角色 |
| UI 交付形态 | 分化 | MCP Apps = iframe 自由但碎片化；A2UI over MCP = 声明式、原生渲染、可治理 |
| 治理层 | 不成立 | MCP 本身不提供布局质量校验、可访问性 gate、回滚、个性化评估 |

更准确的定位：

> **不是“做一个 Web UI 的 MCP”，而是“做一个 MCP/A2UI 之上的 UI 治理运行时”。**
>
> MCP 或 A2UI over MCP 负责“Agent 如何声明 UI 意图”，你的框架负责“声明之后发生什么”：schema 校验、组件白名单、布局质量评估、可访问性硬 gate、快照回滚、用户锁定与偏好持久化。

你不和 MCP 或 A2UI 竞争协议层，而是在它们之上占据一个它们明确不覆盖、但生产落地必须有的层。

## 六、推荐定位

**一句话定位：**

> 面向前端开发者的 Agent-native UI 治理运行时：在 A2UI/MCP 等声明式 UI 协议之上，提供组件目录约束、布局质量评估、可访问性硬 gate、快照回滚、用户锁定和个性化反馈闭环。

**不做：**

- 不做替代 React/Vue 的新前端框架。
- 不做另一个通用 Generative UI 协议。
- 不做“Agent 任意改 DOM/样式”的自由生成。
- 不追求“实时自由编排整个页面”。

**要做：**

- 稳定骨架 + 受约束可变区域。
- 组件白名单和设计令牌。
- 布局质量与可访问性校验层。
- 快照、回滚、灰度、审计。
- 用户“锁定/恢复默认/为什么这样展示”。
- 任务完成率、信息查找时间、错误率、满意度评估。

## 七、MVP 路线建议

1. **选垂直场景**：不要一上来做通用框架。优先 B2B 内部工具/数据看板、客服/运维工作台、电商导购、低代码建站 AI 布局层、Agent 结果展示层。
2. **选 5–8 个组件**：卡片、表格、图表、表单、列表、操作栏、筛选器、空状态。
3. **定义 2–3 种布局原语**：单列、双列、看板、主从。
4. **只做单页/单模块自适应**，不做全站生成。
5. **Agent 只输出 UI Spec，不写代码**；先做“建议布局 + 用户确认后应用”。
6. **内置治理层**：schema 校验、组件白名单、可访问性 gate、性能预算、快照回滚、锁定默认布局。
7. **评估指标**：任务完成率、信息查找时间、错误率、用户满意度、可访问性合规率，而不是“炫不炫”。
8. **协议策略**：优先兼容 A2UI / A2UI over MCP，不另起协议；先做 React adapter，再扩展 Vue/Svelte/Web Components。

## 八、结论

**想法值得做，但必须换叙事和切口。**

- 方向已被验证：A2UI、CopilotKit、json-render、Apex、MCP Apps 等证明“Agent 声明 UI、框架渲染治理”是真实趋势。
- 通用“实时自由编排布局”在 2026 年技术条件下不可靠：协议有缺口、LLM 布局质量弱、可访问性合规率低、实时生成延迟需靠预计算绕过。
- 真正相对空白的是**治理层**：校验、回滚、可访问性 gate、布局质量评估、个性化评估、用户锁定。
- 最务实的产品形态不是“新前端框架”，而是**A2UI/MCP 之上的 UI 治理运行时**，先垂直场景跑通指标，再扩展成框架。

**Go/No-Go 判断标准**：如果你能在 3–6 个月内，在一个垂直场景中做出“Agent 建议布局 → 校验 → 用户确认 → 可回滚 → 指标提升”的闭环，并且治理层被开发者认为“没有它不敢上生产”，这个方向就成立；如果只是做一个更自由的 UI 生成器，竞争不过 A2UI/CopilotKit 生态，且会撞上布局质量和可访问性硬约束。
