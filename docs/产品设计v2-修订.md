## 1. 术语与标注图例

### 1.1 核心术语（首次定义，全文统一用法）

| 术语 | 定义 |
|---|---|
| **spec** | Adapter 从协议层（A2UI 等）收到的原始 UI 声明（JSON）。**不可信输入**。 |
| **IR** | Adapter 将 spec 经显式构造器翻译后的归一化内部表示（Gate 之前）。结构见 §5.1。 |
| **IR′** | Gate 输出的（可能经 fix 修正的）IR，即 `GateResult.ir`。**唯一可渲染对象**（§12）。 |
| **verdict** | Gate 判定结果：severity × action 二维模型（§6.2）。 |
| **commit frame** | 协议消息边界构成的提交帧；Gate 的正式 verdict 只在帧边界产生（§5.2）。 |
| **pending 帧** | 尚未到达 commit 边界的增量帧内容；只能以 inert 形态上屏（§5.2）。 |
| **specHash** | `sha256(canonicalJSON(IR))`。对 IR 计算而非原始字节，规避解析器差异；canonical 规则见 §5.3。 |
| **irPrimeHash** | `sha256(canonicalJSON(IR′))`。 |
| **verdictDigest** | `sha256(canonicalJSON(verdict + trace 规则 ID 序列))`。 |
| **policyHash** | `sha256(编译后的索引化谓词表)`（§7.1 编译产物）。 |
| **catalogHash** | `sha256(catalog bundle)`，bundle = manifests + 审计证明（§8.2）。 |
| **engineVersion** | `@genui/gate` 包的 semver。审计四元组之一：`{irVersion, engineVersion, policyHash, catalogHash}`。 |
| **receipt（提交回执）** | 每个 commit 追加到审计链的记录：`{seq, prevHash, specHash, irPrimeHash, verdictDigest, policyHash, catalogHash, engineVersion}`（§12.2）。 |
| **RenderSource** | Session 创建时签发的会话独占渲染源能力令牌；渲染器运行时只接受由同会话 Gate 经 RenderSource 发出的 IR′（§12.1）。 |
| **zone** | 应用构建期注册的可变区域；敏感组件的准入边界（§13 T1）。 |
| **inert** | 不可聚焦、不可交互、不进入无障碍树的渲染状态（HTML `inert` 属性 + 焦点序剔除）。 |

## 2. 原则与验收定义（修订 v1 §0）

所有设计围绕五条原则。与 v1 的差异：绝对化断言全部改写为「可验证表述 + 验证手段」或显式降级为设计目标。

1. **确定性优先**：Gate 核心为纯函数。可验证命题：同一 fixture 在 Node / Chromium / WebKit 上产出相同的 `canonicalHash(IR′)` 与 `verdictDigest`——CI 跨平台矩阵强制（§15.1）。验证失败即阻断合并。
2. **预算先行**：每个模块开发前先定延迟/内存/体积预算，预算进 CI 门禁（§6.6、§15.6）。本文所有预算数字均为 `[假设，P0 校准点]`，P0 出口标准包含「预算达标或书面重校准」。
3. **信任边界显式化**：Agent 输出（spec）按不可信处理；catalog 与 policy 是可信输入（企业版带签名）；用户动作与宿主应用可信。
4. **降级优于失败 `[设计目标]`**：意图是任何子模块故障不白屏、不崩溃宿主。验证手段：失败矩阵逐行黄金测试 + 管线各级混沌注入（§15.4/§15.5），判定标准：注入实验中宿主零未捕获异常、fallback 渲染率 100%。**已知不可覆盖残余**：运行时级不可恢复故障（OOM、事件循环饿死）不在验证范围内，不承诺覆盖。
5. **隐私默认：遥测本地优先；内容级数据（spec/IR/IR′ 的字段值）默认不外传**（修订 v1「内容零外传」，理由见 §23-A3）。两个**显式例外**，默认关闭、开启需企业配置 + 终端用户告知 + 写入审计链：
   - 例外一：quarantined spec 完整转储——默认仅写本地磁盘环形缓冲，上传远端需显式开启；
   - 例外二：审计级复算导出——企业版 audit-server 复算需要原始 IR（§12.3），需显式开启并受 DPA 约束。
   验证手段：CI 中默认配置遥测载荷 schema 断言（无值字段）+ e2e 网络捕获出口白名单；任一默认载荷含内容字段即构建失败。

## 4. 总体架构与依赖规则

```
┌────────────────────────────────────────────────────────────┐
│ 宿主应用 (React / Vue / 原生)                                │
│   └─ @genui/gate-react 等（薄集成，只依赖 Session API）        │
├────────────────────────────────────────────────────────────┤
│ Session 层（有状态编排）@genui/session                        │
│   ingest → arbitrate → stage/commit 事务 → snapshot →       │
│   telemetry → RenderSource/receipt 签发（§12）               │
├────────────────────────────────────────────────────────────┤
│ Gate 核心（纯函数、零依赖、零 I/O）                            │
│   limits → schema/whitelist → policy → a11y → budget → fix  │
├────────────────────────────────────────────────────────────┤
│ IR 层：归一化 + 防腐（@genui/ir）                             │
├────────────────────────────────────────────────────────────┤
│ Adapters：a2ui（P0）/ mcp-apps、chatkit（后置，可替换）        │
└────────────────────────────────────────────────────────────┘
   Ports（注入，不由核心实现）：Clock / Storage / Logger / Sink
```

**依赖规则**（CI 用 eslint-config/dependency-cruiser 强制）：

- 核心三包 `ir` / `gate` / `policy` 零运行时依赖、无 DOM/Node API，浏览器与 Node 双端可运行（服务端复算依赖此点）；
- 平台差异只经 Port 接口注入；
- `@genui/session` 只依赖核心三包；`@genui/gate-react` 只依赖 session；adapter 只依赖 ir；框架集成包不得触碰核心内部结构；
- axe-core 等 a11y 检查器仅作为**测试期 devDependency**（§15.3），不进运行时依赖图。

包归属与开源/企业划分见 §16（落实评审 D15：v1 §13 发布清单缺 Session 层）。

## 5. IR：归一化与流式语义

### 5.1 节点模型

```ts
interface IRNode {
  id: NodeId;                 // adapter 分配，会话内稳定
  type: ComponentId;          // 对应 catalog 条目；未注册类型 = 白名单外 → block
  props: JsonValue;           // 已过 props schema 的规范化值
  slots: Record<string, IRNode[]>;  // 命名槽位。IR 不含任何空间坐标
  bindings?: BindingRef[];    // 数据绑定，只能引用宿主注册的数据源
  capabilities: Capability[]; // 声明的能力需求（如 needsNetwork）
}
```

**设计决策：IR 没有布局字段。** 空间排列由人工布局模板（catalog 一等公民）持有，Agent 只能选模板、填槽位。依据：「布局与层级是 LLM 主导性弱点」`[未核实，待补一手来源：构想v1 转述 Apple CHI 2026，v2 评审确认无一手出处]`。**该决策独立于引文成立**——即使引文被证伪，「布局质量由人工模板保证」仍是降低方差的最短路径，届时改述理由、不改设计。

### 5.2 流式、提交帧与 TOCTOU 收口（落实评审 A2）

- Adapter 将协议流翻译为操作序列（upsertNode / patchProps / deleteNode），IR 以不可变树 + 结构共享应用；
- 操作按 commit frame 分组。Gate 只在帧边界做完整校验（schema/whitelist/policy/a11y/budget）；帧内只做 `limits` 快速检查（防流式 DoS）；
- **v1 缺陷**：帧内增量渲染只过 limits、不过 whitelist/policy，恶意 Agent 可在 block 生效前把假表单渲染上屏并允许交互（流式 TOCTOU）。
- **修订机制——pending 帧强制 inert**：
  1. 未提交帧的节点一律进入 pending 渲染态：容器挂 `inert`（不可聚焦/不可交互）、`pointer-events: none`、不进入焦点序与无障碍树，视觉标注「待审」；
  2. commit 边界 verdict 为 pass/transform → 摘除 inert、去除「待审」标注；verdict 为 block/requireApproval → 整棵 pending 子树移除 + 走 fallback（§14）；
  3. 判定标准（进 e2e）：pending 期间对目标节点发起 `focus()`/`click()`，断言 `document.activeElement` 不进入 pending 子树、零事件派发；verdict 到达前 pending 子树内不存在任何可交互路径。
- 背压（修订 v1 预算矛盾，落实写作要求 3）：帧队列上限 = **帧数 ≤ 100 且累计字节 ≤ 4 MB，先到者触发溢出**（v1 的 100×256KB=25.6MB 与「会话内存 ≤10MB」矛盾，见 §6.6 构成表）。溢出策略 = 丢弃最旧未处理帧 + 请求 adapter 全量重同步（A2UI `createSurface` 重放；resync 协议写进 adapter 一致性套件 §15.2）。

### 5.3 规范化与哈希（审计基石）

- **Canonical JSON**：键字典序、UTF-8、无空白、数字规范化 → sha256 得 specHash / irPrimeHash。哈希前必须规范化；「杜绝解析器差异」改写为可验证命题：同一 fixture 在 Node/Chromium/WebKit 三端 canonicalHash 一致，CI 矩阵强制（§15.1），不一致即阻断合并；
- IR 解析不用深度合并：原始 JSON 经显式构造器逐字段复制（reviver 白名单），阻断原型污染与多余字段透传；
- 未知字段：**保留但 Gate 忽略**（前向兼容）；未知组件类型：**白名单规则直接 block**（安全优先于兼容）。

### 5.4 版本（落实评审 C10：迁移框架推迟）

- 保留 `irVersion` 字段；审计记录仍落四元组 `{irVersion, engineVersion, policyHash, catalogHash}`；
- **v2 只承诺**：未知 `irVersion` → ingest 期 fail-closed 拒绝 + quarantine + 请求 resync；
- **v1 的「逐版本迁移函数框架」推迟**至首次真实版本升级发生前，不预先建框架（无存量数据时迁移框架是纯开销）。

## 6. Gate 核心：管线、Verdict 与预算

### 6.1 管线（顺序固定，每级短路规则明确）

```
1. limits      硬上限检查（DoS 防线，fail-closed，超限 → quarantine）
2. schema      props 对 catalog manifest 的 JSON Schema 子集校验（§6.5）
3. whitelist   组件/能力/区域 白名单（含 zone 越权）
4. policy      策略引擎（§7）
5. a11y        组合级检查（标题层级/landmark/焦点顺序）
6. budget      性能与内容预算（节点数/文本长度/列表长度）
7. fix         具名修复器串行应用（fix 依赖序编译期定序）
```

### 6.2 Verdict：severity × action 二维模型（沿用 v1）

| | pass | transform | requireApproval | block |
|---|---|---|---|---|
| info | ✅ | — | — | — |
| warn | ✅（记录） | ✅ 自动修 + UI 轻标注 | 可选 | — |
| error | — | ✅ 自动修（可撤销） | ✅ | ✅ + fallback |
| critical | — | — | — | ✅ + fallback + 隔离 |

非法组合（如 critical+transform）在策略编译期报错。verdict 参与 §15.0 幂等性定义的等价关系。

### 6.3 核心契约（纯函数 + effects 分离）

```ts
interface GateResult {
  ir: IRPrime;               // fix 后的 IR′；类型品牌化，只能经 RenderSource 送达渲染器（§12.1）
  verdict: Verdict;          // 最严格 action 胜出
  trace: TraceEntry[];       // ruleId/severity/action/nodePath/before/after
  effects: Effect[];         // 延迟副作用（遥测、快照提示）——由 Session 执行
}
gate(ir: IR, ctx: GateContext): GateResult;
```

Gate 自身不执行遥测、不落快照、不调时钟——副作用以 Effect 值返回。这保证 gate 可在 Node 无副作用复算；复算证明什么、不证明什么，见 §12（v1「双跑验证=信任制高点」的表述已删，见 §23-A1）。

**确定性纪律**（进 code review checklist）：核心禁用 `Date.now()` / `Math.random()` / locale 相关比较；时间相关策略经 `ctx.evaluationTime`（Session 注入）求值；集合遍历使用稳定序（插入序或 ID 序）。

### 6.4 fixer 完备性契约（新增，支撑幂等性）

每条带 fixer 的规则必须满足：**fix 应用后的 IR′ 上，该规则不再触发**。fixer 无法保证完备修复时，禁止注册 transform 路径，只能降级为 requireApproval/block。该契约逐 fixer 用性质测试验证（§15.0）。

### 6.5 schema 校验：受限子集（落实写作要求 3：40KB vs 零依赖矛盾）

v1 同时要求「核心三包零依赖（= 自研 JSON Schema 校验器）」与「gz 合计 ≤40KB」，二者对完整 JSON Schema 实现不兼容。**修订**：propsSchema 只支持受限子集，自研子集校验器按体积预算 §6.6 构成表控制。

子集范围（超出即 manifest 编译错误）：`type`、`required`、`enum`、`const`、数值/长度上下界、`maxItems`、嵌套 object（深度 ≤ 8）、`additionalProperties: false`。**不支持**：`$ref`（catalog 内联展开）、`format`、`pattern`（正则——与 §7.2 规则禁正则的 ReDoS 立场一致）。

### 6.6 DoS 硬上限与性能/内存预算

**limits 硬上限（全部 fail-closed → quarantine；数值均为 `[假设，P0 校准点]`）**：

| 限制项 | 上限 | 依据 |
|---|---|---|
| 树深度 | 32 | 防栈溢出（配合显式栈遍历） |
| 节点总数 | 2,000 | 超限隔离，请求 agent 重发精简版 |
| 单节点子节点数 | 64 | — |
| 单 prop 大小 | 16 KB | 文本类另受 budget 级约束 |
| 单帧总大小 | 256 KB | — |
| fix 链应用次数 | 单帧 ≤ 50 | 防修复器振荡，超次降级 block |

**性能预算（CI bench 门禁；全部 `[假设，P0 校准点]`）**：

| 指标 | 预算 |
|---|---|
| gate 全管线 p99 @500 节点/深度 12 | ≤ 5 ms |
| Session 帧摄入 p99 | ≤ 10 ms |
| 核心三包 + 子集校验器体积（gz 合计） | ≤ 40 KB（构成见下） |
| 会话常驻内存上限 | ≤ 10 MB（构成见下） |

**体积构成**（`[假设，P0 校准点]`，bundlewatch 逐包断言）：ir ≤ 8 KB、gate ≤ 12 KB、policy ≤ 8 KB、schema 子集校验器 ≤ 10 KB，合计 38 KB ≤ 40 KB。若 P0 超限，二选一（决策点 D4）：预算上调至 60 KB，或校验器拆为可选包。

**内存构成**（会话常驻 ≤ 10 MB，`[假设，P0 校准点]`，P0 用 memory sampling 断言）：

| 项 | 上限 | 说明 |
|---|---|---|
| 已应用 IR/IR′ | ≤ 2 MB | 2000 节点规模估算 |
| pending 帧队列 | ≤ 4 MB | 与 §5.2 字节上限同源（先到者触发溢出，解决 v1 25.6MB 矛盾） |
| 快照环形缓冲 | ≤ 2 MB | 结构共享，只计增量（§10） |
| Gate 工作内存（瞬时） | ≤ 1.5 MB | 显式栈 + 校验中间态 |
| 遥测缓冲 + 审计链本地段 | ≤ 0.5 MB | §11/§12 |
| 余量 | ~ | 合计 10 MB 内 |

### 6.7 增量校验：砍掉（落实评审 C9）

v1 §3.4 的「子树哈希 + LRU 记忆表」整体删除。理由：无任何 bench 证据表明全量校验不达 §6.6 预算，属过早优化；记忆表引入失效传播正确性风险，而「miss 退化为全量」意味着它不改变最坏情况。**P0 先全量校验 + bench；若 p99 > 5 ms，先 profile 定位再决定优化，优化方案届时另行评审。**

### 6.8 Gate 自身故障：GateGuard

Gate 抛出任何异常 → GateGuard 捕获 → fail-closed 渲染 fallback + quarantined spec 完整落盘（默认仅本地环形缓冲，上传属 §2-5 例外一）→ 宿主不感知异常。

「Gate 永远不允许崩溃宿主」改写为：**设计目标 + 验证手段**——失败矩阵逐行黄金测试 + 管线每级混沌注入（§15.5），判定标准：注入实验 1,000 次/语料帧 `[假设]` 内宿主零未捕获异常、fallback 渲染 100%。残余风险（OOM 等运行时级故障）显式声明不覆盖（§2-4）。

## 7. 策略系统

### 7.1 分层与合并语义（沿用 v1）

```
baseline（随包发布，WCAG 2.2/EAA 基线 [来源：W3C WCAG 2.2, 2023-10]）
  < org（企业下发，可签名）
  < app（宿主仓库内，走代码评审）
  < runtime（运行时开关，仅能收窄）
```

编译期合并：单调收紧——尝试放宽低层 fail-closed 规则 → 编译错误（带规则 ID）；同层冲突 → 编译错误；编译产物 = 索引化谓词表（按组件类型分桶），Session 创建时编译一次，其哈希即 policyHash，渲染期零解析开销。

### 7.2 规则模型：数据，不是代码

```yaml
- id: table-requires-caption
  match: { component: Table, props: { caption: absent } }
  check: derivesFromDataSchema
  severity: warn
  action: transform
  fixer: captionFromSchema     # 具名修复器，内置实现，非任意代码
  zone: any
  message: "表格缺少可访问名称，已从数据字段推导补齐"
- id: password-field-zone
  match: { component: PasswordInput }
  check: inZone
  severity: critical
  action: block
  zone: [secureForm]           # 安全区构建期注册，Agent 不可写
```

- match 是数据，check/fixer 是内置具名谓词/修复器。「策略文档永远不可执行任意代码」改写为可验证命题：规则 schema 为封闭字段集（无 code/expression 字段），fuzz 测试构造含代码形态字段的策略文档 → 断言 100% 编译期拒绝（§15.5）；企业自定义谓词走 WASM 沙箱（P3，暂缓）；
- 规则内禁止正则；确需模式匹配的内置谓词使用有界匹配（编译期校验长度上限），防 ReDoS。

### 7.3 执行灰度：shadow 手动开关（落实评审 C11：分片灰度推迟）

每条规则 `mode: off | shadow | enforce`，**仅支持手动切换**。

- shadow：只记录本应触发的 verdict，不影响渲染。上线任何新规则建议先过 shadow 期（≥ 7 天或 ≥ 10k 帧 `[假设，P0 校准点]`）；
- v1 的 `userIdHash % 100 < cohort` 队列分片灰度**推迟**：MVP 无多租户流量基础，分片机制在单试点团队上是空转；shadow 数据用于计算「预估拦截率」，超阈值规则要求人工评审后再手动 enforce——这仍是「a11y gate 误拦率高导致弃用」风险的解法；
- 灰度不允许无人值守自动升档（沿用 v1）。

### 7.4 策略测试（沿用 v1）

规则 × 样例 spec 期望 verdict 矩阵；CI 用录制语料回放新旧两版策略 diff verdict digest；企业签名策略包版本固定、禁止降级。

## 9. 仲裁与应用事务

### 9.1 提案状态机（单写者语义）

```
proposal ──stage──► staged(preview) ──commit──► applied ──► locked | reverted | superseded
   ▲                     │ abort                     │
   └─────────────────────┴───────────────────────────┘（新提案可重新进入）
```

- 同一 zone 同时只允许一个 staged 提案：新提案到达 → 旧提案 aborted（或按策略排队）。「写冲突在状态机层面消除」的判定标准：性质测试断言任意提案序列下不存在两个 zone 内并存 staged（§15.1）；
- 两阶段提交：stage 时完成 Gate 校验并生成 IR′ + diff，commit 时落快照并应用。**预览与最终渲染消费同一个 IR′ 对象**（同一 RenderSource 签发，§12.1），「杜绝预览和上线不一致」的判定标准：e2e 断言预览与 commit 渲染的 irPrimeHash 相等。

### 9.2 优先级仲裁（固定求值序，结果进 trace）

```
用户锁定（zone 级硬停） > 用户偏好 > 平台策略（zones/预算） > Agent 提议
```

确认策略由 policy 决定：`user-confirm`（运营侧默认）/ `auto`（低风险白名单变更，消费者自助页默认，配「恢复默认」入口）/ `never`。仲裁全程确定性——「为什么这样展示」直接由 trace 渲染，**禁止 LLM 生成解释**（沿用 v1：解释的可验证性优先于流畅性）。

## 10. 快照与回滚（落实评审 C8：状态快照推迟）

**MVP（P0/P1）默认路径 = spec 回滚 + 状态丢弃提示**：

| 设计点 | 决策 |
|---|---|
| 快照点 | 仅 commit 边界 |
| 内容 | `{ irPrimeHash, IR′ 根引用（结构共享）, focusHint（best-effort）, inflight: AbortToken[] }` |
| 缓冲 | 内存环形 N=20 `[假设，P0 校准点]`；持久化快照（IndexedDB/加密）P2 |
| 进行中请求 | Session 注册 AbortToken，回滚即取消；未注册的存量请求不承诺取消 |
| 回滚执行序 | 取消 inflight → 暂停摄入 → 恢复 IR′ → 恢复焦点（best-effort）→ 恢复摄入 |
| 状态丢失 | 表单输入、滚动位置等组件状态**不恢复**，回滚后明确提示「已恢复布局，部分输入未保留」；提示文案有快照测试（§15.4） |
| 防投毒 | 快照带 irPrimeHash，恢复时校验，不匹配即丢弃该快照 |

**含组件状态的序列化/重水化推迟至 P2 决策**（v1 将其列为 MVP 显式验证项）。理由：serializer 契约、8KB/64KB 预算、重水化失败降级路径是独立子系统，占 v1 快照章节一半复杂度，而其收益（表单中途回滚保留输入）在消费者自助页试点中未经验证。P2 决策证据：试点中「状态丢失提示」出现频率 + 用户抱怨率 `[假设，P1 采集]`；若数据显示状态丢失是弃用主因，再立项。**本表同时删除 v1 失败矩阵的「重水化失败」行——功能不存在则不为其写降级承诺。**

## 11. 遥测与指标（落实评审 B7：核心指标可辨伪）

### 11.1 事件模型

| 事件 | 内容 | 默认 |
|---|---|---|
| verdict | ruleId/severity/action/计数 | 开（**不含 spec 内容**，§2-5） |
| userAction | rollback/lock/confirm/revert/edit-then-confirm/ignore + zoneId + 事件序 | 开 |
| perf | 各阶段耗时（10% 采样 `[假设]`） | 开 |
| contentShape | props 类型形状指纹（无值） | 关（opt-in） |

本地窗口聚合（30s 或 100 条批量 `[假设]`），导出 OTLP 或自定义端点；离线有界磁盘队列 1 MB，溢出丢最旧并计数。用户 ID 仅以按组织加盐哈希出现。opt-out 时完全本地化。

### 11.2 第一代指标（可辨伪口径）

v1 缺陷：「锁定率下降」无法区分「因满意而不改」与「因不信任而不碰」——语义相反，不可用作 Go/No-Go。**修订**：单指标全部降级为诊断量，Go/No-Go 用组合口径：

```
提案交互事件分类（按 zone，7 天滑窗）：
  acceptAsIs        确认且未编辑
  acceptAfterEdit   编辑后确认
  rollback          应用后回滚/恢复默认
  ignore            提案超时/abort，零交互
  lock              锁定（区分 activeLock：该 zone 此前有 ≥1 次 accept/edit；
                    dormantLock：此前零交互）

健康度组合（阈值全部 [假设，P0 校准点]，试点前由作者拍板或授权按数据定）：
  交互率   = (acceptAsIs + acceptAfterEdit + rollback) / proposals ≥ 30%
             —— 低于阈值 = 用户没在看 Agent 编排（不信任或无感），
                此时任何「回滚率低」都是假绿，判 No-Go 信号
  直接接受率 = acceptAsIs / (acceptAsIs + acceptAfterEdit + rollback) 随周数上升
  回滚率   = rollback / applied 随周数下降
  休眠占比 = dormantLock / (dormantLock + activeLock) 不升
```

```
gate 拦截率   = blockedFrames / committedFrames（诊断量）
自动修复率   = transformedFrames / committedFrames（诊断量）
预估→实际差  = shadow 期预估拦截率 vs enforce 后实际拦截率（校准 §7.3）
```

反 gaming 原则：所有指标度量用户可观测行为（事件序 + 时间窗定义见 §11.1 userAction），不采信 Agent 自评。判定标准的实现：指标口径单测进 §15（给定合成事件流，断言各口径计算结果与语义解释，含「低回滚 + 低交互 = 假绿」用例，见 §17-P1 出口③）。

## 12. 信任链与审计（重写，落实评审 A1）

### 12.0 v1 的错误与二选一

v1 称双跑验证是「信任制高点」，把「客户端是否执行了治理」变成可验证命题——**这是错的**。服务端复算只证明**判定函数的确定性**（该 spec 在该策略下应得该 verdict），不证明**客户端渲染的就是过闸的 IR′**。v2 在两个方案中选 **(b) 客户端执行 + 渲染源绑定**，后果与残余风险如实写明。

选择 (b) 的理由：(a) 服务端权威 Gate 与「治理不进服务端串行链路、不依赖服务端可用性」的架构原则（构想v1 §五-1）直接冲突，且引入延迟与单点；(b) 保持客户端执行，用渲染源绑定把「绕过」变成可检测事件。选择 (b) 不排他：核心零依赖可跑 Node，若未来客户合规框架要求权威判定，(a) 可作为企业部署模式叠加（audit-server 用同一代码复算裁决），不构成架构锁死。

### 12.1 渲染源绑定机制

1. Session 创建时签发 **RenderSource**（会话内随机 nonce + 品牌化类型）；
2. `gate()` 返回的 IR′ 只能经 RenderSource 送达渲染器：`@genui/gate-react` 的渲染入口运行时校验「该 IR′ 由本会话 Gate 在本 Session 内发出」，非 Gate 产物（原始 spec/IR、跨会话 IR′、伪造对象）→ 拒绝渲染 + 发审计事件；
3. 预览与 commit 渲染消费同一 IR′（§9.1），e2e 断言两者 irPrimeHash 一致。

### 12.2 回执哈希链

每个 commit 追加 receipt（定义见 §1.1）到 append-only 哈希链（含 prevHash）。链上记录绑定「渲染源哈希」：审计方可对账 `irPrimeHash` 序列与渲染器实际提交渲染的哈希序列。

### 12.3 服务端复算：证明什么、不证明什么

- **证明**：对给定 specHash + 四元组，verdict 是否正确（判定函数正确性与确定性）；
- **证明（结合 §12.1/12.2）**：若客户端绕过 Gate 渲染非 IR′ 对象，会产生「渲染器拒绝事件 / 回执链断裂 / irPrimeHash 对账缺口」——即**篡改可证（tamper-evident）**；
- **不证明**：被完全攻陷的客户端不伪造整条链。**「不可绕过」不在承诺范围内**；该级别的保证需要方案 (a) 或硬件远程证明，均超 MVP 范围。对外叙事禁用「信任制高点」「不可绕过」类表述。
- 复算输入：企业审计模式显式开启 spec 导出（§2-5 例外二）；未开启时复算仅在客户自有部署（audit-server on-prem）内执行，spec 不出企业边界。

### 12.4 GDPR 冲突处理与导出（沿用 v1，补验证口径）

哈希链只存假名化摘要；可选明细 blob 按用户密钥加密，删除密钥即等效擦除 `[设计目标]`——判定标准：法务 DPIA 意见 + 密钥删除演练（删除后解密断言失败）列入 P2 出口（§17）。导出：签名 JSONL bundle + manifest，对接企业 SIEM。

## 15. 测试与验证策略

### 15.0 幂等性定义（修订 v1，落实评审 E16）

v1 断言 `gate(gate(x).ir) ≡ gate(x)` 在 trace 上不成立（二次运行 fixer 不再触发，trace 必然不同）。**修订**：等价关系定义在 `(IR′, verdict)` 对上，trace 不参与等价：

```
let (ir1, v1) = gate(x)
let (ir2, v2) = gate(ir1)
断言 1（IR 不动点）：canonicalHash(ir2) == canonicalHash(ir1)
断言 2（verdict 投影）：v2 == project(v1)
  project: pass→pass, transform→pass, requireApproval→requireApproval, block→block
```

transform→pass 的成立依赖 §6.4 fixer 完备性契约，逐 fixer 用性质测试在语料上验证。

### 15.1 性质测试（property-based）

§15.0 幂等性；§9.1 单写者（任意提案序列无并存 staged）；transform 单调性；跨平台确定性（同一 fixture 在 Node/Chromium/WebKit 产出相同 canonicalHash(IR′) 与 verdictDigest，CI 矩阵强制）。

### 15.2 语料回放与 adapter 套件

录制真实 Agent 流 100+ fixtures 作黄金语料（消费者自助页 + 看板 dogfooding 两场景），adapter/策略/引擎变更全部过回放 diff；adapter 一致性套件对损坏流做模糊测试（截断、交错、超长、循环引用、重复 ID），新协议接入必须先过套件。

### 15.3 render smoke test（新增，落实评审 E17）

对语料中每个 committed IR′ 做 headless React 渲染（jsdom + 真实浏览器双跑）：

- 断言：零未捕获异常、零 console error；
- 断言：axe-core 快照与 golden 一致（axe 仅测试期 devDependency，不违反核心零依赖）；
- 效果：v1 开放问题 1 的「dev-time a11y 钩子」由候选升级为 **CI 质量门禁**——渲染后可达性问题在合并前拦截，Gate 运行时承诺仍限于静态分析（§8.2）。

### 15.4 降级路径黄金测试（落实评审 E18）

§14 失败矩阵每行的 fallback 渲染、quarantine 本地转储、degrade 用户提示各配快照测试；新增断言：默认配置下转储载荷不出现在任何网络出口（与 §2-5 网络捕获测试共用 egress 白名单）。

### 15.5 混沌注入与出口白名单

管线每级边界挂故障注入点；CI 对语料帧随机抛异常（每语料 1,000 次迭代 `[假设]`），断言：宿主零未捕获异常、fallback 渲染率 100、quarantine 事件必发。策略 fuzz：含代码形态字段的策略文档 100% 编译期拒绝。e2e 网络捕获：默认配置下出口域名白名单外零请求。

### 15.6 预算 CI

§6.6 bench（固定种子数据）、bundlewatch 构成表、内存构成采样，全部进 CI。

## 19. 定价与商业化（新增章节，落实评审 D13；全部为待验证假设）

**计费维度候选**（P2 前只访谈不实现）：

| 维度 | 理由 | 风险 |
|---|---|---|
| 环境数（staging/prod × 站点） | 审计/合规价值按生产环境计；与开发者免费使用解耦 | 多站点大客户单价跳变 |
| 席位（策略作者/审批人） | 策略管理是多人协作功能，天然按人头 | 席位套利 |

**付费触发点排序**（按假设的紧迫度）：① EAA 申报/审计应对（法规 deadline 驱动）→ 审计报告包；② 多团队策略统一管理 → 签名分发；③ 事故追责/证据链 → audit-server；④ SLA/私有化部署。排序本身是假设，验证成本见 §20-A1。
